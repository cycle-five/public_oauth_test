About the Login Test Pages

What these pages are for, what they promise, and how to check it. Try them: strict · accept-any · script login

Purpose

These pages exist to test credential fillers, password managers and credential brokers, and in particular to find out what a browser stores after a submitted login. Typing into a form is one thing; a real submission is what makes browsers offer to save, and write rows to their login stores.

Nothing typed here leaves your machine. A service worker answers the form posts itself, so the request never reaches the network or GitHub Pages.

The variants

URLWhat it is
/login.htmlStrict login: only the public pair testuser / correct-horse-battery-staple succeeds. Real form POST.
/login/any.htmlAccept-any: any non-empty username and password succeeds. Real form POST. (A canary test uses this, since a canary can never be the public password.)
/login/spa.htmlScript login (accept-any): a fetch() POST, then the form is removed from the DOM and the URL changes via history.pushState (no document navigation).
/login/welcome.htmlLanding page after success: no username or password field, says "Logged in", with a Log out link back to where the login came from.

Selectors and states

  • #login-form: the form. Gains data-ready="true" once the worker controls the page.
  • #username, #password, #submit: the fields and the button.
  • #login-status: status box; its data-state is idle, error or not_ready on the login pages, and success on the welcome page.
  • #login-status-text: the human-readable text inside the status box.
  • #fill-report: carries data-username-length and data-password-length, the character counts currently in the fields (lengths only, never values).

How values stay on the machine

The service worker (/sw.js, registered with scope: '/login') intercepts three endpoints and answers them itself: POST /login/session/strict, POST /login/session/any and POST /login/api/session. The classic pages get a 303 redirect; the script page gets JSON {"ok": ...}. The request never reaches the network.

The worker reads the body, compares, answers and forgets: no logging, no Cache Storage, no IndexedDB, no stored variable, and nothing from the request is echoed into a URL (the error and from words are fixed). There is deliberately no session state: the welcome page does not show the username, because a synthetic worker response cannot set a cookie.

Fail-closed rules

  • The inputs live in a <fieldset disabled> that is enabled only after the worker is confirmed controlling the page (data-ready="true"). Until then the status is not_ready.
  • Disabled controls are excluded from submission, so even a filler that calls form.submit() early sends an empty body and no value reaches GitHub Pages.
  • A hard reload (Shift+Reload) loads the page outside the worker. It stays disabled and says "Reload this page normally"; it does not auto-reload.
  • With no JavaScript at all, the fieldset stays disabled.

Content-Security-Policy

Each page sets default-src 'none' with form-action 'self', worker-src 'self', base-uri 'none' and inline style and script. /login/spa.html additionally needs connect-src 'self' for its fetch. These were the only directives the design needed.

How to run a control

Use the reproducible harness tests/storage-control.mjs. Run it with a fresh --user-data-dir, a chosen login URL, typed versus script-set values, and optionally a managed policy. It reports table names and row counts only, never values.
