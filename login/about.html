About the Login Test Pages

What these pages are for, what they promise, and how to check it. Try them: strict · accept-any · script login · script login, form kept

Purpose

These pages exist to test credential fillers, password managers and credential brokers, and in particular to find out what a browser stores after a submitted login. Typing into a form is one thing; a real submission is what makes browsers offer to save, and write rows to their login stores.

Nothing typed into the login pages leaves your machine. A service worker answers the form posts itself, so the request never reaches the network or GitHub Pages.

The variants

URLWhat it is
/login.htmlStrict login: only the public pair testuser / correct-horse-battery-staple succeeds. Real form POST.
/login/any.htmlAccept-any: any non-empty username and password succeeds. Real form POST. (A canary test uses this, since a canary can never be the public password.)
/login/spa.htmlScript login (accept-any): a fetch() POST, then the form is removed from the DOM and the URL changes via history.pushState (no document navigation).
/login/spa-keep.htmlScript login, form kept (accept-any): the same fetch() POST, but on success nothing is taken away. The form stays in the DOM with its values still in the fields, the URL does not change, and the status becomes success. For testing what a filler does with a filled form once the login has gone through, such as clearing the fields.
/login/welcome.htmlLanding page after success: no username or password field, says "Logged in", shows the submit receipt, with a Log out link back to where the login came from.

Selectors and states

  • #login-form: the form. Gains data-ready="true" once the worker controls the page.
  • #username, #password, #submit: the fields and the button.
  • #login-status: status box; its data-state is idle, error or not_ready on the login pages, and success on the welcome page and on /login/spa-keep.html after a login (where the form also gains data-logged-in="true").
  • #login-status-text: the human-readable text inside the status box.
  • #fill-report: carries data-username-length and data-password-length, the character counts currently in the fields (lengths only, never values). It is live: on /login/spa-keep.html it drops to 0 / 0 when the fields are cleared after a login.
  • #submit-report: the submit receipt, the character counts that were in the fields at the moment of the last successful submit, as data-username-length and data-password-length, with data-recorded="true". It does not change afterwards, so it can be read at leisure. It is on the welcome page, in the logged-in panel of /login/spa.html, and under the form of /login/spa-keep.html. Where no submit was seen it says data-recorded="false" and has no lengths (a script calling form.submit() fires no submit event, so it leaves no receipt).

Checking a fill without reading it back

A fill and a submit can both finish between two looks at the page, and then the fields are gone. The submit receipt is the page's own reading, taken inside the submit: lengths always, and equality on request.

For equality, open any login page with ?expect= followed by the SHA-256 (64 lowercase hex characters) of username:password in UTF-8. The receipt then carries data-match="true" or "false". The comparison happens in the page; the digest is never shown, and a value that is not 64 hex characters is ignored.

printf '%s:%s' "$username" "$password" | sha256sum

The digest travels in the URL, so it does reach the web server and the browser history. Use it only for a long random canary, never for a password someone could guess.

How values stay on the machine

The service worker (/sw.js, registered with scope: '/login') intercepts three endpoints and answers them itself: POST /login/session/strict, POST /login/session/any and POST /login/api/session. The classic pages get a 303 redirect; the script page gets JSON {"ok": ...}. The request never reaches the network.

The worker reads the body, compares, answers and forgets: no logging, no Cache Storage, no IndexedDB, no stored variable, and nothing from the request is echoed into a URL (the error and from words are fixed). There is deliberately no session state: the welcome page does not show the username, because a synthetic worker response cannot set a cookie.

The one thing a classic login page keeps is the submit receipt: two character counts, and a yes/no when ?expect= was given, in this tab's sessionStorage under login-test:last-submit, so the welcome page can show it. No value is in it, and a login page removes it when it loads. The script pages keep the receipt in the page and store nothing.

Fail-closed rules

  • The inputs live in a <fieldset disabled> that is enabled only after the worker is confirmed controlling the page (data-ready="true"). Until then the status is not_ready.
  • Disabled controls are excluded from submission, so even a filler that calls form.submit() early sends an empty body and no value reaches GitHub Pages.
  • A hard reload (Shift+Reload) loads the page outside the worker. It stays disabled and says "Reload this page normally"; it does not auto-reload.
  • With no JavaScript at all, the fieldset stays disabled.

Content-Security-Policy

Each page sets default-src 'none' with form-action 'self', worker-src 'self', base-uri 'none' and inline style and script. /login/spa.html and /login/spa-keep.html additionally need connect-src 'self' for their fetch. These were the only directives the design needed.

Observed storage results

Measured with Google Chrome 158 on Linux, a fresh profile per run, the browser closed before the files were read. Row counts and table names only — never the stored values. Three stores are checked: Login Data → logins (a credential actually saved), Login Data → stats (a save was offered and dismissed), and Web Data → autofill (the username recorded as form history).

Protectedaccept-any, typed, password manager + autofill disabled000

What this shows:

  • The fix works. A submitted login on the new pages makes Chrome offer to save (stats = 1) and record form history (autofill = 1). The old page (run C) left stats = 0 because its preventDefault() meant the browser never saw a submission — that was the defect.
  • logins stays 0 everywhere: an unattended browser never clicks "Save", so no credential is actually written. The save was offered, not accepted.
  • Script-set values behave exactly like typed ones (run B = run A): a value written by a filler (native setter + synthetic input/change) is treated the same as keystrokes.
  • Headless Chrome runs the save logic too (A headless = A): the bubble can't be shown, but the stats and autofill rows still appear.
  • A failed login was not trace-free (run D): a wrong password still left stats = 1 and autofill = 1. The likely cause is that the redirect back to the login page briefly presents a disabled password field (the fail-closed state), which Chrome can read as "the login form is gone" and so offers to save anyway. Treat this as observed behaviour, not a guarantee.
  • A locked-down browser stored nothing (Protected): all three counts were 0. Caveat: this run disabled the password manager and autofill through a per-profile preference (credentials_enable_service=false), which emulates an enterprise managed policy (PasswordManagerEnabled=false, AutofillAddressEnabled=false, AutofillCreditCardEnabled=false) without installing a system-wide policy. A real managed policy lives in /etc/opt/chrome/policies/managed/.

How to run a control

Use the reproducible harness tests/storage-control.mjs. It serves the repo, launches a real Chrome with a fresh --user-data-dir, performs the login, then reports table names and row counts only — never values. Flags:

  • --url the login page to drive (default /login/any.html)
  • --mode typed|script real keystrokes, or a value set by script with synthetic events
  • --policy none|protected baseline, or password manager + autofill disabled
  • --headed|--headless and --channel chrome|chromium

For example, run A above was node tests/storage-control.mjs --url /login/any.html --mode typed --policy none --headed --channel chrome.
